# PictoRust – ephemeral Rust relay

This is an isolated, **room-capability-gated prototype with experimental client-side AES-256-GCM and ephemeral P-256 sender signatures**. It is not a replacement for a reviewed secure messenger and must not be deployed publicly.

- Binds only to `127.0.0.1:8787`.
- Serves a **development-only** browser client at `http://127.0.0.1:8787/` with Unicode text, canvas sketches and local print-to-PDF. The browser encrypts outgoing text and strokes with the standard Web Crypto API (AES-256-GCM), using a separate manually shared 256-bit chat key that is never sent to the relay. The UI now has DS-inspired dual screens, a DE/TR touch keyboard, drawing undo and local print-to-PDF.
- Browser UI uses no third-party assets, stores no chat in localStorage, and adds a strict local-only CSP, no-store cache policy, and no-referrer header. Every outgoing message is signed with an ephemeral non-extractable P-256 signing key and then AES-256-GCM encrypted; recipients verify an explicit externally exchanged public-key fingerprint before displaying it. Page reload rotates this ephemeral identity, requiring out-of-band re-verification. Do not use it for confidential data.
- Accepts legacy experimental signed-browser binary envelopes of 29–16384 bytes with version byte `2` (12-byte IV and >=16-byte GCM tag); drops oversized, plaintext-shaped and text messages. This is **structural validation**, not proof that a frame is real ciphertext.
- **MLS test transport v3:** also accepts opaque frames `[0x03, kind, MLS TLS payload]` where kind is `1` application, `2` Commit, `3` Welcome or `4` KeyPackage. The relay merely checks framing and 3–16384-byte length and broadcasts the bytes unchanged; it neither authenticates nor decrypts MLS messages. The existing browser remains on protocol v2. The independently tested OpenMLS v3 library has not been integrated into the actual browser UI. A real OpenMLS-to-WebSocket test runs in `mls-lab/tests/websocket.rs`. **Do not infer group membership security from acceptance of a v3 frame.**
- **Stateless temporary invitations:** `POST /new-room` (loopback only) returns a random 32-hex room ID and HMAC-signed bearer token in a `Cache-Control: no-store` JSON response. The ID contains a creation timestamp; new websocket admissions for these rooms expire after 6 hours. Room IDs do not identify users, and no database is created. Existing connected sessions are disconnected at their room's expiration deadline. Previously issued administrative room IDs remain valid until root secret rotation. A leaked invitation may be reused until expiry, even after a room becomes empty.
- Room IDs are exactly 32 lowercase hex digits. Each room additionally requires a 256-bit HMAC-SHA256 bearer capability; possession of this token permits joining, but does not prove individual identity.
- Temporary room creation is capped at **32 requests per 60 seconds across this relay process**. Once exhausted, the endpoint returns HTTP 429. This deliberately coarse process-wide quota is not IP-based anti-DDoS protection.\n- At most 256 active rooms. Inactive rooms are reclaimed at the next join.
- Each room accepts at most 16 concurrent WebSocket sessions; over-capacity handshakes receive HTTP 503. Slots are released when a session ends.
- At most 128 concurrent upgraded WebSocket sessions (extra handshakes receive HTTP 503).
- Each connection has a fixed one-second quota of 20 binary messages. The entire room also has a shared 64-frames/second quota to prevent coordinated participant floods. Exceeding either quota terminates the sending connection. This is a basic abuse guard, not fairness across IPs or identities.
- Browser WebSocket origins are restricted to `http://127.0.0.1:8787` and `http://localhost:8787`. Non-browser clients can omit the Origin header, so this is **not authentication**.
- Retains recent frames only in a bounded `tokio::broadcast` buffer while subscribers hold a room. Once all room handles are dropped, the room and its buffer are freed.
- Does not store chats to disk, use a database, or include external service integrations.
- HMAC room capabilities provide basic admission, **not** individual identities or forward secrecy. For honest participants using the browser and an independently shared strong chat key, the relay receives AES-GCM ciphertext rather than text or drawings. However, the server cannot verify that a client actually encrypted its payload, and a hostile participant with the shared key can impersonate others. Browser replay detection is bounded and resets upon reconnect. No per-IP fairness or MLS group-key management yet.

From `server/`, generate an independent 32-byte root secret using `openssl rand -hex 32`, then export it as `PICTOCHAT_RELAY_SECRET` (never commit it). Generate an admission token with `cargo run -- invite 0123456789abcdef0123456789abcdef`. A client connects to `ws://127.0.0.1:8787/ws/<room-id>` with WebSocket subprotocol values `["picto.v1", "auth.<token>"]`; the server echoes only `picto.v1`. Rotate the root secret to revoke all tokens; individual revocation is not yet supported. **Only use test data until E2EE exists.**

Generate a **separate** random 256-bit chat key with `openssl rand -hex 32`; do NOT use the relay root secret or room admission token as the chat key. Start `cargo run` from this directory, visit `http://127.0.0.1:8787/` and click **Raum + Einladung erstellen** in the first tab. Share the room ID and bearer token over a secure independent channel. In a second tab, enter the same invitation. Compare the displayed ephemeral session fingerprints via a **different verified channel**, paste the verified peer fingerprints into the respective trusted devices fields, then enter the same separate chat key in each. Never send the chat key over PictoChat. Send drawings or text; use the print button and select a local PDF printer to export the visible conversation. Two-peer browser interaction, Unicode rendering, original sprite geometry, PDF raster and actual two-page A4 pagination are exercised by the Chromium workflow. Only these tested paths are covered; no external security audit has been performed.

Run `cargo test` and `cargo run` from this directory. Do not expose the development port through a reverse proxy, container network mapping or firewall.

Next gate: authenticated **temporary** device membership and revocation, forward secrecy through an audited client-side MLS integration, replay protection across reconnects, client code integrity and independent security review before allowing non-loopback binds. Permanent accounts and long-lived device identities are explicitly NOT part of the product.
